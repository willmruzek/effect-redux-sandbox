# Prove the layers

The tracker is a reference application, not a requirement for using the store
packages. The executable [inventory consumer](../tools/layer-examples/src/)
uses public exports, its own domain types and no tracker/application imports.
It requires neither a browser nor a running backend.

## Run the examples

From the workspace root, after `pnpm install`:

```sh
pnpm --filter './packages/*' --recursive run build
pnpm --filter @repo/layer-examples test
pnpm --filter @repo/layer-examples typecheck
```

Root `pnpm test` and `pnpm typecheck` also include this consumer and build its
workspace dependencies first. The examples run through deterministic tests,
not a new application or development server. Transport responses and persistence
are injected at the I/O boundary.

## Progressive adoption

| Stage | Redux | Effect | Consumer proof |
| --- | --- | --- | --- |
| Core only | Plain `redux` store and handwritten reducer | `@repo/effect-store`, handwritten reducer and app-owned runtime | [core examples](../tools/layer-examples/src/core.ts), [tests](../tools/layer-examples/src/core.test.ts) |
| Optional slices | Official Redux Toolkit `createSlice` | `@repo/effect-store-toolkit` `createSlice` | [slice examples](../tools/layer-examples/src/slices.ts) |
| Optional requests | `@repo/redux-toolkit` | `@repo/effect-store-toolkit` | [Redux inventory](../tools/layer-examples/src/reduxRequests.ts), [Effect inventory](../tools/layer-examples/src/effectRequests.ts) |

Slices require no request definitions or request metadata. Request examples
install the generated API reducer once and use slices for standalone write
case registration; this is composition, not a core-store requirement.
The Effect toolkit package includes request utilities
in the same public entry point, so importing only `createSlice` proves API
optionality, not a separately packaged or measured smaller bundle.

The [boundary tests](../tools/layer-examples/src/boundaries.test.ts) check actual
production manifests and example import declarations. The Effect core has no
internal workspace dependencies. The two request toolkits depend on the
store-independent transport package, not either app or tracker domain. The
transport package has no production dependencies.

This is public-export consumer evidence within the monorepo, not an isolated
published-package installation test. The comparison harness intentionally
installs both implementations. Bundle size, publication and standalone packed
artifact validation are not claimed.

Our packages are focused store and request-lifecycle primitives, not replacements
for the broader cache and synchronization features of TanStack Query or RTK
Query. The repo uses Redux Toolkit, but does not use RTK Query. For feature
details, see the official [TanStack Query overview](https://tanstack.com/query/latest/docs/framework/react/overview),
[RTK Query overview](https://redux-toolkit.js.org/rtk-query/overview) and
[RTK Query cache behavior](https://redux-toolkit.js.org/rtk-query/usage/cache-behavior).

### Cursor pagination

Each toolkit exports `createCursorPagination`, `CursorPaginationState` and
`PaginationAction`. A definition supplies state accessors, cursor extraction
and a domain merge, then installs its reducer alongside the generated API
reducer. Its `next` and `refresh` Effects take a stable store service and a
canonical identity covering filters, sort and source. `next` skips duplicate
pending pages and exhausted chains; `restart: true` explicitly requests page
one. `refresh` always requests page one and supersedes older pending pages.
Failures and interruptions retain the last successful chain and allow retry.
Only an eligible, valid page merges and advances the cursor in one reducer
transition. A page claiming more results must supply a new non-null cursor.
Cursor equality uses `Object.is`, so use scalar cursors or stable references.

The `query` callback receives the chosen cursor and request metadata and can
call a generated operation's `runWithResult`; its successful outcome contains
the normalized result. It shares the same in-flight execution as `run` for the
same operation, stable store-service object and canonical variables. `run`
retains its original outcome shape. The optional `execute` callback instead
accepts a cursor and abort signal and returns a page directly.

Generated query success handlers run before `runWithResult` returns. When
composing with pagination, do not independently merge the page in that handler:
install the pagination reducer and merge there so stale or invalid pages cannot
commit early. Validate cursor invariants during normalization as well if query
success metadata must reflect a cursor error. The tracker apps follow this
pattern. Their result `pageInfo` is the last successful response snapshot used
to initialize hydrated state; pagination state is the execution authority.
There is no pagination hook, automatic fetch or response cache. See the
[public consumer tests](../tools/layer-examples/src/pagination.test.ts) for
headless examples.

### Manual request hooks

The optional [`@repo/request-react`](../packages/request-react/README.md)
package provides `useQuery` and `useMutation` for generated operations from
either toolkit. The hooks observe store-owned metadata for their bound
variables and expose explicit triggers; they do not automatically fetch or
return normalized entities. Their public-export React tests use real Redux and
Effect stores. Tracker workflows and standalone write lifecycles are unchanged.

The source and Effect-facing service must refer to the same store. Sharing a
pending read additionally requires the same stable service object used by other
callers. A wrapper around an app's privately held workflow service does not
automatically share its in-flight execution.

### Shared in-flight reads

[0006](../plans/0006-share-in-flight-reads.md) adds query sharing without a response
cache or a new Promise API. `run` remains a lazy Effect: identical queries using
the same operation definition and stable receiving store service object await
one execution and its original success, failure or superseded outcome.
External callers may receive different Promise objects around that execution.
The first caller supplies the transport options and Effect context; later
callers do not execute their own fetcher or callback.
With synchronous store services, execution still publishes loading state and
starts transport immediately. A duplicate launched by a started-action observer
joins the already registered execution.

Each caller owns a wait, not the transport. Cancelling the first caller or a
duplicate stops only that wait. When the last waiter leaves, the worker is
interrupted and ownership cleanup completes before cancellation finishes.
A caller arriving during that cleanup waits before starting a fresh execution.

Each toolkit independently keeps its reference-counted worker registry outside
reducer state. One execution publishes one started action and one settlement
lifecycle, retaining the existing latest-wins and explicit-registration guards.
Success, failure, publication defects and interruption release the registry
entry. Subsequent calls perform fresh reads; no completed result is retained.
Pending query metadata without a corresponding local execution fails explicitly.

Sharing applies only to normalized queries. Duplicate normalized mutations still
skip, and standalone write lifecycles still reject duplicate writes. App workflow
preflight can still avoid a query entirely; sharing only applies when callers
actually execute the request API.

### Generated API reducer

[0007](../plans/0007-generated-api-reducers.md) replaces normalized per-action
registration with `api.reducer(state, action)`. It handles request metadata for
all defined queries and mutations, including start ownership, supersession,
success, failure and cancellation. Apps install it once in reducer composition;
definitions do not install behavior in a store automatically.

Optional `operation.reducer({ onStarted, onSuccess, onFailure })` creates a
separate guarded domain reducer. Compose it before `api.reducer` so callbacks
see pre-transition ownership. Apps still own their initial state, normalized
entities, visible domain notices and merge rules. No domain callbacks are needed
for an operation to execute and update generic request metadata.

This matches the generated-reducer integration convenience of RTK Query without
introducing its endpoint-cache state shape or middleware. Our API reducer uses
the existing root-state metadata accessor. Standalone write lifecycles still
require explicit case registration.

## Side-by-side tracker read: load the next task page

### 1. UI dispatches an app-owned workflow

- [Redux adapter](../apps/redux-first/src/components/ReduxClientApp.tsx):
  `onLoadMore` dispatches `loadMoreTasks`.
- [Effect adapter](../apps/effect-first/src/components/EffectClientApp.tsx):
  `onLoadMore` dispatches the matching Effect workflow.

The shared UI knows callbacks and state, not store services or request APIs.

### 2. Each workflow reads its receiving store

| Redux | Effect |
| --- | --- |
| [store workflows](../apps/redux-first/src/store.ts) obtain `ReduxStore` | [flows](../apps/effect-first/src/flows.ts) obtain `EffectStore` |
| [middleware](../apps/redux-first/src/effectMiddleware.ts) supplies the service and executes external programs through the app runtime | [core store](../packages/effect-store/src/index.ts) supplies the service and executes external programs through the app runtime |

Each workflow checks current loading/exhaustion state, prepares query/cursor
variables and chooses the transport. GraphQL uses the operation document;
REST supplies an execution callback. Mixed mode keeps people ownership separate.

### 3. The normalized request runner publishes lifecycle actions

The app-owned definitions are
[Redux](../apps/redux-first/src/trackerApiDefinition.ts) and
[Effect](../apps/effect-first/src/trackerApiDefinition.ts).
They supply decoding, normalization and scope. API creation also generates the
metadata reducer; the receiving store explicitly installs it.

The runner computes the canonical request key, claims request ownership and
publishes `trackerApi/tasks/started`. Duplicate pending queries join the existing
execution instead of publishing another started action. The boundary
response is decoded and normalized before `succeeded`; failures publish
`failed`, and interruption cleanup can publish `cancelled`.
Latest-wins ownership guards prevent an older read settling over a newer one.

### 4. Domain and generated API reducers update data

[Redux reducer composition](../apps/redux-first/src/trackerApiReducers.ts) and
[Effect reducer composition](../apps/effect-first/src/trackerApiReducers.ts)
run guarded domain reducers before the generated API reducer.
Domain callbacks update visible notices and merge normalized entities/result
membership using shared helpers; the API reducer owns request metadata.
No second GraphQL response tree or endpoint-result cache is stored.

### 5. The store publishes; the projection and UI react

Redux subscriptions/React Redux and the Effect snapshot binding notify their
respective adapters. The shared
[database projection](../packages/project-tracker/src/database.ts) reconciles
store entities into read-only collections. The
[tracker UI](../packages/project-tracker/src/ProjectTracker.tsx) renders live
joins and derives request notices from the same store-owned state.

The stores own data; the relational projection does not become another write
authority. Hydrated navigation state remains app-owned, and this workflow
does not add a second initial browser fetch.

## Side-by-side optimistic write: save task status

### 1. Domain preflight

Both `saveStatus` workflows read their own store and call
[validateTaskEdit](../packages/project-tracker/src/taskValidation.ts) with
`field: 'status'`. Missing tasks, drafts, pending deletion and a pending status
save produce explicit domain errors. Each app surfaces an invalid result with
`Effect.fail(new Error(error))` before executing transport or applying optimism.

Validation explains whether an operation is allowed. It is not a lock or a
replacement for authoritative backend validation.

### 2. Lifecycle execution

App definitions in
[Redux](../apps/redux-first/src/trackerOperations.ts) and
[Effect](../apps/effect-first/src/trackerOperations.ts) provide a pending-record
accessor. The workflow supplies `{ taskId, value }` and `execute(signal)`.
The runner generates a request ID and publishes `tracker/statusStarted`.

### 3. Explicit optimistic transition

[Redux operation cases](../apps/redux-first/src/trackerOperationReducers.ts)
and [Effect operation cases](../apps/effect-first/src/trackerOperationReducers.ts)
register guarded field callbacks. Started saves the original status and
request ID before replacing the entity's status with the optimistic value.
Subscriptions, the projection and the UI observe that ordinary action.

The start guard checks eligibility again. If no handler claims ownership,
the runner fails explicitly instead of performing an untracked write.

### 4. Confirm or roll back

- Success publishes `tracker/statusConfirmed` with original input metadata
  plus the authoritative saved status under `result`.
- Failure publishes `tracker/statusFailed`, restores the original status and
  records a visible error.
- A stale owner cannot settle the newer write.
- Changed start eligibility does not stop an existing write settling.

Reducers contain only data; transport, Effects and runtime resources stay outside.

### 5. Refresh is a workflow decision

After a successful backend write, each workflow explicitly calls `refreshTasks`.
Injected status persistence intentionally does not trigger that automatic
workflow refresh. Refresh reloads the first backend page; no cache invalidation
engine or atomic multi-page refresh is implied.

## Second domain: inventory quantities

[Inventory contracts](../tools/layer-examples/src/inventory.ts) use SKU keys,
labels and non-negative integer quantities. There are no task IDs, drafts,
projects, people or tracker source modes.

Both request implementations:

- Decode unknown transport data and verify the requested SKU.
- Normalize entities keyed by SKU.
- Define their own pending accessors and numeric field transitions.
- Install the generated API reducer once; explicitly register standalone writes.
- Validate quantity writes in the consumer workflow before starting a lifecycle.
- Accept an authoritative saved quantity differing from the optimistic value.
- Roll back persistence failure with visible error data.

The [request contract tests](../tools/layer-examples/src/inventory.test.ts)
exercise both implementations against the same observable cases: reads,
malformed responses, optimism, confirmation, rollback, missing registration,
invalid input, duplicate requests, stale confirmation and store isolation.
Domain fixtures are independent of tracker code. Typed input and result
assertions are also checked by the consumer's TypeScript command.

The minimal inventory read merge replaces incoming records. Unlike tracker
merging, it does not reconcile a read overlapping a pending quantity write.
Such domain conflict policy is intentionally outside these isolated scenarios;
do not copy that simple merge into a concurrent editing app without defining it.

## Public API ergonomics: verified findings

| Observation from the consumer | Trade-off / recommendation |
| --- | --- |
| `createRequestLifecycle<State, Result>()` needs a typed pending accessor to infer input | Explicit ownership is useful; show the accessor near the definition instead of adding a hidden default |
| `createRequestApi` needs a typed `getState` to anchor standalone state inference | Document the annotation; do not invent initial-state ownership in API definitions |
| Effect slices return creators from a builder callback; Redux uses its official reducer object | Keep this intentional difference visible rather than forcing a cast-based common abstraction |
| Read and write action unions compose through `RequestActions` | Use the inferred union for the consumer service; avoid widening it to arbitrary payloads |
| The API reducer handles every read case; three standalone write cases still require explicit registration | Install the API reducer once; keep domain handlers separate and compose them first |
| Runners need only an Effect-valued state/dispatch service | Redux can adapt synchronous store methods without importing the tracker middleware |
| Core external Effect dispatch uses an application-owned runtime | Dispose it explicitly; service-level request execution can instead compose in a caller-owned Effect |
| Domain preflight and reducer start guards have different jobs | Keep both visible; do not treat eligibility as generic request mechanics |

The Redux inventory example invokes programs through `Effect.runPromise` with
its structural service adapter; it does not demonstrate external
`redux.dispatch(effect)`. The real Redux tracker supplies that behavior through
its app middleware. The Effect inventory workflow uses core external Effect
dispatch. This deliberately demonstrates both the runner's minimal contract
and the existing execution-placement difference, not identical dispatch APIs.

The original second-domain proof needed no public API changes. Later approved
plans added shared query execution and generated API reducers, and the examples
now use those contracts. Neither change adds a shared cross-store engine,
compatibility shim, automatically installed reducer or response cache.

## Local frontend data

The tracker now demonstrates [plan 0008](../plans/0008-local-data-ownership.md)
in both stores: task stars live in local companion records and scratch notes live
in a local-only table. App-owned table declarations describe ownership; explicit,
validated synchronous actions change local data without transport. The UI reads
both tables through the same read-only projection, including an optional
task-preference left join.

Confirmed deletion removes preferences; draft confirmation remaps them while an
existing server-ID preference wins. Remote failures leave independent local
changes intact. These tables start empty for SSR/hydration and are in-memory
only; offline synchronization and durable storage are separate roadmap items.

For official Redux slice registration and dispatch inference background, see
[Redux Toolkit TypeScript usage](https://redux-toolkit.js.org/usage/usage-with-typescript)
and [createSlice](https://redux-toolkit.js.org/api/createSlice).
