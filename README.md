# effect-redux-sandbox

A proof of concept for Redux + Effect and Effect-Redux state management.
The goal is to demonstrate reusable, understandable patterns while developing
libraries that can serve as replacements for RTK Query and TanStack Query.

- **Redux + Effect** combines Redux Toolkit's store and reducers with
  Effect-based workflows and request execution.
- **Effect-Redux** uses a custom Effect-first store with Redux-style actions
  and reducers, plus independent Effect-based request tooling.

Both approaches power **Fieldwork**, a TanStack Start project-tracker demo
with store-owned data and read-only TanStack DB live queries.

## Layers

| Layer | Redux-first | Effect-first |
| --- | --- | --- |
| Store | Redux with Redux Toolkit | `@repo/effect-store` |
| Slices and requests | `@repo/redux-toolkit` | `@repo/effect-store-toolkit` |
| React integration | React Redux | `@repo/effect-store-react` |
| Optional manual request hooks | `@repo/request-react` | `@repo/request-react` |
| Domain and projections | `@repo/project-tracker` | `@repo/project-tracker` |

Each app owns its store composition, runtime, workflows, transport choices
and domain merge policy. The request toolkits are independent; shared packages
provide transport utilities, tracker domain logic and read-only projections.
See [COMPARISON.md](COMPARISON.md) for dispatch, request lifecycles and demo
behavior, and [Prove the layers](docs/prove-the-layers.md) for side-by-side
traces and runnable public-API examples.

## Comparison with query libraries

| Capability | TanStack Query | RTK Query | Our Redux / Effect libraries |
| --- | --- | --- | --- |
| Server-state fetching | ✅ Built in | ✅ Built in | ✅ Built-in execution; explicit app-owned integration |
| Managed request state | ✅ Library-managed query state | ✅ Generated API reducer | ✅ Generated API reducer installed once; separate app-owned domain handlers |
| Data-selection hooks | ✅ `useQuery` with `select` for query data | ✅ `selectFromResult` for endpoint data | 🟡 `useStoreSnapshot` reads the full Effect store; no dedicated selector hook |
| Request-status hooks | ✅ Query status/error and fetching-count hooks | ✅ Endpoint `useQueryState` and mutation status | ✅ Manual operation hooks observe keyed request status and errors |
| Mutation / workflow-trigger hooks | ✅ `useMutation` supplies a mutation trigger | ✅ `useMutation` and `useLazyQuery` supply triggers | 🟡 Manual query/mutation operation triggers; arbitrary workflow binding is not included |
| Automatic fetch-on-mount hooks | ✅ `useQuery`, subject to query options | ✅ `useQuery`, subject to endpoint options | 🧭 N/A — route loaders and app workflows own fetching |
| Generated endpoint-specific hooks | ❌ Generic hooks; custom wrappers are app-defined | ✅ Generated by the optional React entry point | 🧭 N/A — no endpoint hook generation |
| Endpoint response cache | ✅ QueryClient cache | ✅ Redux API cache | 🧭 N/A — normalized entities live in app-owned store state instead |
| Request identity | ✅ Query key | ✅ Endpoint and arguments | ✅ Canonical request keys and app-defined scopes |
| Duplicate pending reads | ✅ Deduplicated | ✅ Cached/shared for matching endpoint arguments | ✅ Shared execution/outcome per operation, store service and canonical key |
| Freshness and cache lifetime | ✅ Configurable | ✅ Subscription-based lifetime and refetch options | 📋 Planned — library-owned freshness and retention policies |
| Background refetch | ✅ Configurable refetch policies | ✅ Configurable refetch behavior | 📋 Planned — currently explicit app refresh |
| Mutation invalidation | ✅ Query invalidation | ✅ Tag invalidation | 📋 Planned — currently apps choose whether to refresh |
| Optimistic writes | ✅ | ✅ | ✅ Optional field reducers; apps define transitions |
| Failure rollback | ✅ | ✅ | ✅ Field helper restores the original value and records an error |
| Stale-settlement protection | ✅ | ✅ | ✅ Explicit request ownership and latest-wins guards |
| Decode and normalize responses | 🟡 Query function or schema integration | 🟡 Endpoint transforms or base query | ✅ App-defined contracts and shared entity utilities |
| Transport choice | ✅ Query function | ✅ Base query or endpoint logic | ✅ GraphQL helper or app-supplied execution |
| Pagination | ✅ Query and infinite-query patterns | ✅ Endpoint patterns | ✅ Headless library-owned cursor workflow; app-owned transport and merges |
| Domain rules and merge policy | 🟡 App-defined | 🟡 App-defined | ✅ Explicitly app-owned |

**Legend:** ✅ Yes · ❌ No · 🟡 Kind of (see note) · 🧭 N/A (intentionally
different or out of scope, not a missing implementation) · 📋 Planned.
Cells marked "Planned" describe roadmap goals, not implemented capabilities.

Our packages currently focus on store and request-lifecycle primitives; the broader
cache and synchronization features of TanStack Query and RTK Query remain
roadmap items. The repo uses Redux Toolkit, but does not use RTK Query. See the
[layer comparison guide](docs/prove-the-layers.md#comparison-with-query-libraries)
for shared-read semantics and official documentation references.

## Library roadmap

Unchecked items are planned additions, not current capabilities. Each needs a
numbered implementation plan defining ownership,
public APIs, failure/cancellation behavior and test-first acceptance before work
begins. Keep normalized entities store-owned and domain merge rules app-owned;
this roadmap does not require an endpoint response cache.

- [x] **Library-owned cursor pagination:** reusable headless cursor mechanics
  manage progression, refresh and exhaustion; apps supply transport, cursor
  extraction and domain merge policy. See [plan 0010](plans/0010-library-cursor-pagination.md).
- [ ] **Freshness and cache lifetime:** add configurable freshness and retention
  policies for normalized query membership/metadata, with explicit entity
  retention and eviction ownership.
- [ ] **Background refetch:** add library-owned scheduling and configurable
  triggers, with defined active-query ownership and cancellation.
- [ ] **Mutation invalidation:** let mutations declare affected query scopes and
  let the library mark them stale/refetch according to the configured policy.
- [x] **Manual request hooks:** expose generated query and mutation triggers,
  status and errors without requiring React components to inspect store
  metadata. Subscriptions do not automatically start requests; see
  [plan 0009](plans/0009-manual-request-hooks.md) for scope and limitations.
- [x] **Local-only entity tables:** declare local ownership and support validated
  synchronous writes without transport or request lifecycles.
- [x] **Local companion tables:** attach local attributes to remote entities by
  ID without sending them to the server or overwriting them during remote merges.
- [x] **Reactive local-data projections:** include local tables in TanStack DB
  projections and optional joins, updating the UI without fetching.
- [x] **Local-data lifecycle policies:** define deletion, temporary-ID,
  retention and SSR hydration behavior; remote rollback must preserve independent
  local changes.
- [ ] **Durable local storage:** persist and restore selected normalized data,
  with schema migrations, retention and storage-failure handling.
- [ ] **Offline reads:** make persisted data available without connectivity and
  expose when it is stale or unavailable.
- [ ] **Offline writes:** retain local changes and queue remote mutations for
  later synchronization without losing work across restarts.
- [ ] **Reconnect and replay:** resume queued work when connectivity returns,
  with ordering, retries, cancellation and duplicate-submission safeguards.
- [ ] **Conflict resolution:** detect and surface synchronization conflicts,
  with explicit app-owned resolution and server coordination policies.
- [ ] **Synchronization visibility:** expose connectivity, pending work,
  failures and conflict status so apps can communicate and recover.
- [ ] **Multi-tab coordination:** define how tabs share persisted changes and
  coordinate synchronization without creating competing write authorities.

The local-data items are covered by
[plan 0008: Local data in the frontend database](plans/0008-local-data-ownership.md),
now **IMPLEMENTED**. Offline-first capabilities require separate
plans; they are not included in plan 0008 or implemented today.

The checklist is not an execution order. Dependencies and behavior choices will
be established in the individual plans; other deferred features remain out of
scope.

## Development

Install dependencies with `pnpm install`, then run:

```sh
pnpm lint
pnpm typecheck
pnpm test
pnpm build
```

Start either app with `pnpm --filter @repo/redux-first dev` or
`pnpm --filter @repo/effect-first dev`. On a fresh checkout, build shared
packages first with `pnpm --filter './packages/*' --recursive run build`.
Root test, typecheck and build commands handle this automatically.

Follow the [readable-code skill](.agents/skills/readable-code/SKILL.md) for
whitespace and logical grouping.

### Effect source reference

[repos/effect](repos/effect/) is a read-only squashed Git subtree pinned to
`effect@4.1.2`. It is excluded from application builds and linting; apps import
the installed dependency, never the subtree. See [AGENTS.md](AGENTS.md) for
reference requirements.

When upgrading Effect, update the dependency and subtree to the same version
from a clean worktree (the subtree command creates a local commit):

```sh
git subtree pull --prefix=repos/effect \
  https://github.com/Effect-TS/effect.git \
  'effect@<version>' --squash
```

Update the version references in this README and AGENTS.md afterward.
